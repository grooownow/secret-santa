# Liftkit — дизайн MVP

## 1. Что это

Платный приватный template-репозиторий: **agent-native SaaS-стартер для Claude Code**.
Пользователь покупает доступ, клонирует репо, запускает одну команду — и агент ведёт его
от идеи до работающего локального SaaS-проекта.

**Позиционирование:** не «бойлерплейт с агентскими правилами» (это уже делают supastarter,
MakerKit), а **агентский процесс с тонким скелетом**. Продаём упакованный workflow
«идея → спеки → работающий проект», а не код и не скиллы.

## 2. Целевая аудитория

- **Основной сегмент:** соло-разработчик / инди-хакер с опытом, уже пользуется Claude Code,
  хочет быстро запускать SaaS-MVP. Платит за сэкономленное время (подтверждено рынком:
  ShipFast 7 500+ покупателей по $199–299; supastarter ~$12k/мес).
- **Вторичный сегмент:** специалист смежной роли (QA, DevOps, бэкендер) — терминала не
  боится, но фуллстек-стек SaaS для него тёмный лес; ему ценнее всего ведение за руку.
- **Не аудитория:** новички без опыта (уходят в Lovable/Bolt), сеньоры-скептики HN
  («зачем платить, есть бесплатное»).

## 3. Ключевые выводы ресёрча рынка (2026-07-08)

- Рынок бойлерплейтов жив (~$50M/год) и ИИ его усилил: агенты работают лучше от
  опинионированного скелета (тезис Open SaaS/Wasp).
- Ниша «agent-ready» уже занята как _фича_ инкумбентов (supastarter «Claude Code
  boilerplate», MakerKit «AI-Agent Optimized», VibeReady). Никто не продаёт
  _упакованный процесс_ — это и есть whitespace.
- Голые скиллы коммодитизированы ($0 у aitmpl.com, платные €5–15). Продавать скиллы
  нельзя — продавать можно интегрированный опыт.
- Доминирующая модель продаж: разовая покупка → приватный GitHub-репо
  (Gumroad/LemonSqueezy). Маркетплейс плагинов Claude Code без платежей.
- Каналы: build-in-public (X), Product Hunt, Indie Hackers, партнёрки.

Оговорка: выводы основаны на поисковой фазе deep-research; фаза верификации источников
не завершилась (лимит сессии). Перед лендингом перепроверить цифры цен конкурентов.

## 5. Структура репозитория

```

├── src/                    # тонкий скелет Next.js: app/, features/, components/, lib/, db/ (см. 5.7)
├── .claude/                # плагин Liftkit: скиллы (см. 5.2)
├── docs/
│   ├── manifest.md         # паспорт проекта (заполняет /liftoff)
│   ├── roadmap.md          # заготовка плана после старта
│   ├── rules/              # правила — короткие тематические файлы (см. 5.9):
│   │                       #   architecture, frontend, testing, security, git, docs
│   ├── decisions/          # ADR-lite: журнал решений (заполняет агент)
│   ├── specs/              # спеки фич (генерит агент)
│   ├── templates/          # шаблоны: spec, PRD, idea, decision
│   ├── playbooks/          # пошаговые спеки-планы: инженерные + бизнесовые (см. 5.5)
│   └── qa/project-profile.md  # преднаполненный профиль для qa-pilot (см. 5.4)

├── AGENTS.md / CLAUDE.md   # вход + конвенции репо для агента (короткие, ссылаются на rules/)

├── LICENSE.md              # коммерческая лицензия покупателя

└── docker-compose.yml      # опциональный локальный Postgres (дефолт — PGlite)
```

### 5.1 Скелет кода (тонкий)

Предсобрано только инвариантное для любого небольшого SaaS:

- Next.js (App Router) + TypeScript strict + Tailwind + shadcn/ui;
- дизайн-токены (единый источник, без хардкода стилей);
- auth-заготовка (провайдер выбирается на этапе плана реализации; кандидат по умолчанию —
  Auth.js/NextAuth с email + OAuth). Жёсткое требование к любому провайдеру: сессия —
  stateless JWT в cookie, проверяемая локально; никаких сетевых вызовов к auth-сервису
  на каждый переход (см. 5.6);
- Drizzle + Postgres: локально **PGlite** по умолчанию (embedded Postgres, ставится как
  npm-пакет — ноль системных зависимостей), docker-compose — опция, `remote` — любой
  connection string. Один и тот же SQL/миграции во всех режимах; схема-заготовка `users/…`;
- **полная тестовая архитектура** (см. 5.4) + quality-гейты: линт и форматтер (см. 5.7),
  typecheck (strict), CI-workflow;
- слот аналитики: преднастроенная интеграция провайдера продуктовой аналитики
  (PostHog или Plausible — решается на этапе плана), включается env-переменной;
  события с первого дня, чтобы не «доливать потом»;
- feature-first структура каталогов с enforce-нутыми границами (см. 5.7).

**Не входит:** лендинг, дашборд, биллинг, emails, продуктовые страницы — их генерит
агент под идею пользователя через спеки.

### 5.2 Плагин: скиллы

- **`/liftoff`** — единственный входной скилл-онбординг (см. 6). Проходится один раз.
- Тулбокс (используется после старта, /liftoff знакомит с ним в конце):
  - **feature** — цикл «спека → реализация → **тесты** → ревью» (дистилляция kro-glo-feature,
    упрощённая и без внешних зависимостей вроде Linear). Шаг тестов обязателен, не
    опционален: пользователь полагается на агента, значит доверие держится на тестах.
    Наследует правило qa-pilot «докажи, что тест умеет падать»;
  - **review** — параллельное адверсариальное ревью диффа;
  - **verify** — прогон всех гейтов (юниты, интеграционные, e2e, lint, typecheck)
    - смоук в браузере;
  - **deploy** — ведёт по плейбуку деплоя (Vercel + управляемый Postgres, env, домен).
- Принцип: минимум скиллов, каждый самодостаточен, никакого «зоопарка на все случаи жизни».

### 5.3 Bootstrap

Prerequisites сжаты до минимума: **Node LTS + pnpm + git** (+ `claude` CLI).
Docker НЕ обязателен (локальная БД — PGlite). Java и других рантаймов нет.

`pnpm bootstrap` (или `./scripts/bootstrap`):

1. проверка prerequisites — чего-то нет → скрипт/агент называет недостающее и
   **предлагает установить сам** (brew / официальный установщик) с явным
   подтверждением пользователя; системные установки — никогда молча;
2. установка зависимостей;
3. `.env` из `.env.example`;
4. инициализация локальной БД (PGlite) + миграции + seed;
5. финальное сообщение: «открой `claude` и набери `/liftoff`».

Ошибки не глотаются: каждая падает с действием для пользователя.

Единая дверь: CLAUDE.md в корне встречает пользователя инструкцией «набери
`/liftoff`» — даже проигнорировав README, промахнуться мимо входа нельзя.

### 5.4 Тестовая архитектура и интеграция с qa-pilot

Контроль качества — часть ядра продукта: покупатель полагается на агента, значит
коробка обязана дать ему полную тестовую обвязку и процесс, а не «vitest в devDependencies».

**В скелете предсобрано (универсальная обвязка):**

- юнит/компонентные тесты: vitest + Testing Library, примеры-образцы;
- интеграционные тесты API: vitest + отдельная тестовая БД (локально — PGlite-инстанс,
  в CI — настоящий Postgres сервисом GitHub Actions), фабрики/фикстуры данных —
  общие с seed-скриптом (5.1);
- e2e: Playwright с преднастроенными проектами (desktop/mobile), smoke-набор
  на скелетные страницы;
- `docs/rules/testing.md` — конвенции тестирования, дистиллированные из референсов
  qa-pilot (e2e-patterns, flakiness-catalog, quality-rules): что покрывать на каком
  уровне, анти-flaky правила, запрет false-green;
- CI: один workflow, гоняющий все уровни; красный = не мержим.

**Интеграция с qa-pilot (companion-плагин, без дублирования кода):**

- qa-pilot — публичный плагин Кати; Liftkit его не копирует, а рекомендует:
  bootstrap предлагает установить (`/plugin marketplace add grooownow/qa-pilot`);
- Liftkit шипит **преднаполненный `docs/qa/project-profile.md`** под свой
  фиксированный стек — покупатель пропускает `/qa-pilot:onboard` и сразу
  пользуется `/qa-pilot:cover` для каждой новой фичи;
- разделение ответственности: скиллы Liftkit (`feature`/`verify`) закрывают
  повседневный цикл «фича с тестами и гейтами», qa-pilot — глубокую QA-работу
  (audit, план сценариев, exploratory-сессии в браузере);
- бизнес-синергия: Liftkit приводит пользователей qa-pilot и наоборот
  (кросс-промо в README обоих).

### 5.5 Плейбуки

Плейбук = пошаговая спека-план в `docs/playbooks/`: агент пользователя ведёт по ней,
когда придёт время. Это НЕ скиллы (принцип «минимум скиллов» сохраняется) и не
гарантируемые коробкой сценарии (см. 7).

**Инженерные:**

- **deploy** — Vercel + управляемый Postgres (Neon/Supabase), env, домен;
- **billing** — Stripe: тарифы, чекаут, вебхуки, портал подписки.

**Бизнесовые** (идея ролей подсмотрена у OSS-аналогов, контент пишем свой —
дистилляция опыта Кати: mrr-lab, fortnoise, pawfile; чужие промпты не копируем,
у источника нет лицензии):

- **pricing** — упаковка ценности в тарифы/подписку, расчёт себестоимости
  (включая токены ИИ + время), апселлы;
- **landing** — продающая страница: структура, конверсия, отзывы, воронка;
- **analytics** — какие метрики мерить с первого дня (источники, покупки, отвалы),
  события, дашборд; работает в паре со слотом аналитики в скелете (5.1);
- **compliance** — персональные данные: что собираем, где храним, согласия,
  удаление по запросу. База — GDPR, с заметкой об адаптации под юрисдикцию
  пользователя (152-ФЗ и др.). Особо важно для SaaS с чувствительными данными;
- **ai-integration** — как встроить ИИ-фичи в продукт пользователя: Claude API,
  паттерны (генерация, извлечение, чат), стоимость и кэширование, границы качества.

MVP-объём: каждый плейбук в версии «lite» (1–2 страницы, проверенный скелет шагов);
углубление — по фидбеку покупателей.

### 5.6 Фронтенд: отзывчивость как инвариант

Мотивация: типовые провалы агентских приложений — полная перезагрузка страницы на
каждый клик (не-SPA навигация) и сетевой вызов к auth-сервису на каждый переход
(заметная задержка каждого действия). Liftkit обязан исключить это архитектурно:
правила зашиты в скелет, докс и гейты — агент не может их нарушить незаметно.

**Архитектурные правила (в скелете + `docs/rules/frontend.md`, дистилляция
vercel-react-best-practices):**

1. **SPA-навигация всегда:** внутренние переходы только через `<Link>` (клиентская
   мягкая навигация + prefetch), полная перезагрузка — запрещена. ESLint-правило
   ловит `<a href>` на внутренние пути и `window.location`-навигацию.
2. **Auth без сети на каждый клик:** сессия — stateless JWT в cookie, middleware
   делает только дешёвую локальную проверку cookie; полная валидация — в слое
   доступа к данным. Паттерн «`getUser()` по сети в middleware на каждый запрос»
   (классическая причина лагов с Supabase) — запрещён и описан в docs как анти-паттерн.
3. **Мгновенный отклик на действие:** мутации — оптимистичные (`useOptimistic` /
   optimistic update в клиентском кэше): UI меняется сразу, сервер подтверждает
   фоном. Любой клик даёт видимую реакцию < 100 мс.
4. **Загрузка без «белых экранов»:** server components для первичного рендера,
   streaming + `loading.tsx` со скелетонами (не спиннерами); данные, к которым
   возвращаются, — в клиентском кэше, повторный визит мгновенный.
5. **Без водопадов и тяжёлых бандлов:** параллельные фетчи, server components по
   умолчанию, `use client` только на листьях, тяжёлые компоненты — dynamic import.

**Гейты (проверяемо, не на честном слове):**

- Lighthouse CI на скелетных страницах: Performance ≥ 90, INP < 200 мс — красный CI
  при деградации; входит в golden-path прогон;
- скилл `verify` включает перф-чек: навигация без full reload, отклик действий;
- скилл `feature` на шаге ревью проверяет соблюдение правил 1–5 для нового кода.

### 5.7 Архитектура кода, линт и форматирование

Один язык на весь проект (TypeScript, фронт и бэк — одна кодовая база Next.js),
поэтому один набор инструментов покрывает всё; отдельного «линтера для бэкенда»
не нужно — серверный код проходит те же проверки + strict typecheck.

**Архитектура: одна, универсальная (вариантов не даём — тот же принцип, что
«один стек»).** Feature-first, FSD-lite — синтез проверенного на fortnoise
(бизнес-логика вне компонентов) и pawfile (фичи-слайсы), без полного церемониала
FSD и без монорепо:

```
src/
├── app/            # только маршруты и layout'ы — тонкие, без логики
├── features/       # <feature>/ — слайс: ui + actions + queries + тесты рядом
├── components/ui/  # переиспользуемый UI (shadcn), без бизнес-логики
├── lib/            # ядро: auth, flags, utils; server-only помечен
└── db/             # drizzle-схема, миграции, клиент
```

Правила направления импортов (это и есть «правила архитектуры», enforce-ится
линтером, не доками): `app → features → components/lib/db`; фичи не импортируют
друг друга напрямую (только через публичный `index.ts` слайса); `components/ui`
и `lib` не знают о `features`; доступ к БД — только из слоя queries/actions
фичи или `lib`, никогда из компонентов. Роут-файл — тонкий: парсинг → вызов
фичи → рендер.

Почему это решает дилемму «маленький vs большой проект»: слайсы растут
добавлением, не перестройкой — маленький проект это 3 фичи, большой — 30, но
структура и правила те же. Агент на `/liftoff` и `feature` всегда генерит новую
функциональность как слайс — предсказуемо для ревью и тестов. Монорепо
(pawfile-стиль) в коробку не берём: для небольшого SaaS это лишний вес; вынос в
packages — описан как эволюционный шаг в architecture.md.

**Линт и формат (быстрое + строгое, всё преднастроено):**

- **oxlint** — основной линтер (corrrectness/suspicious/perf правила, мгновенный
  — агент гоняет его после каждой правки без боли);
- **ESLint (flat) — только архитектурный слой**: eslint-plugin-boundaries
  (направление импортов по схеме выше), запрет внутренних `<a>`/`window.location`
  (правило 5.6-1), запрет клиентского импорта server-only модулей,
  `no-restricted-imports` для обхода публичных API слайсов. Дублирующиеся с
  oxlint правила отключены (eslint-plugin-oxlint);
- **Prettier** + tailwind-плагин (сортировка классов — единообразие
  агент-генерённого кода);
- одна команда `pnpm lint` (oxlint → eslint → prettier-check → tsc --noEmit),
  она же в CI и в скиллах `feature`/`verify`. Пользователь про «два линтера»
  не думает — это внутренность коробки.

### 5.8 Надёжность, безопасность, наблюдаемость

Инварианты настоящего приложения, которые агенты стабильно забывают — поэтому
они предсобраны в скелете, а правила закреплены в `docs/rules/security.md`:

**Ошибки и наблюдаемость:**

- обработка ошибок из коробки: `error.tsx` / `global-error.tsx` / `not-found.tsx`
  на каждом уровне, дружелюбные состояния (не стектрейс пользователю);
- структурированный логгер (pino) с конвенцией: серверные ошибки всегда логируются
  с контекстом; `console.log` в продуктовом коде запрещён линтом;
- слот error-трекинга (Sentry), включается env-переменной — как слот аналитики;
- правило «тихих провалов нет»: пустой catch и проглоченный promise — красный линт.

**Безопасность (baseline, не опция):**

- валидация всех входов на границе: каждый server action / route handler начинается
  с zod-схемы; невалидированный вход — анти-паттерн в docs;
- типизированные env-переменные (zod-валидация при старте): отсутствие обязательной
  переменной валит приложение на старте с внятным сообщением, а не в рантайме;
- security-заголовки преднастроены; helper рейт-лимита для публичных эндпоинтов;
- гигиена секретов: `.env*` в gitignore, правило для агента «секреты никогда в код
  и никогда в коммит»; `pnpm audit` в CI (уровень high — красный);
- CSRF/сессии — закрыты выбором Auth.js-паттерна из 5.1.

**Инварианты продукта, о которых забывают:**

- SEO-минимум: metadata API на каждой странице, `sitemap.ts`, `robots.ts`,
  OG-заготовка — шаблон в скелете, агент заполняет под идею;
- доступность: eslint-plugin-jsx-a11y + базовые правила в `docs/rules/frontend.md`
  (семантика, фокус, контраст через дизайн-токены);
- тёмная тема: дизайн-токены двухтемные из коробки (shadcn это даёт почти
  бесплатно) — агент-генерённые страницы наследуют обе темы автоматически;
- email-слот: auth по умолчанию OAuth-first (GitHub/Google — без почтовой
  зависимости); транзакционная почта — слот провайдера (Resend), включается env,
  полноценные email-флоу — плейбуком;
- seed-данные и жизненный цикл дев-данных:
  - `scripts/seed` + фабрики (общие с тестами) — дев-среда с данными одной командой;
  - **сид растёт вместе с доменом**: /liftoff при адаптации схемы генерирует фабрики
    и сид-пак под сущности идеи пользователя (реалистичные записи каждой сущности,
    связанные между собой), скилл `feature` расширяет их при каждой новой сущности —
    пользователь никогда не стартует с пустого экрана;
  - `pnpm db:reset` — пересоздать локальную БД (миграции + сид) одной командой:
    штатный путь при ломающей смене схемы в разработке;
  - **прозрачность хранения** (пользователь всегда знает, где данные и что их
    переживает): README + финальное сообщение bootstrap + /liftoff явно говорят —
    локальные данные живут в `.pglite/` (переживают рестарты; вне git; теряются при
    удалении каталога/свежем клоне), бэкап = копия каталога, долгоживущие данные =
    docker/remote-режим, прод = управляемый Postgres;
- конвенции миграций: применённые миграции не редактируются, только новые;
  generate → review → migrate; правило в `docs/rules/architecture.md`.

**НЕ входит в скелет v1 (осознанно, чтобы не раздувать):** i18n, фоновые
джобы/cron, файловые аплоады, multi-tenancy, realtime. Каждое — кандидат в
плейбук-бэклог фазы 3; агент может добавить их по запросу пользователя, но
коробка не преднастраивает.

### 5.9 Документация как система и конвенции для агента

Документация — интерфейс между сессиями агента, поэтому у неё свои правила
(`docs/rules/docs.md`):

- **Короткие тематические файлы, не монолит:** `docs/rules/` — architecture,
  frontend, testing, security, git, docs (по образцу fortnoise `docs/rules/*`).
  Агент читает только релевантное правило, не весь свод — экономия контекста;
- **CLAUDE.md / AGENTS.md — короткие:** вход, карта ссылок на rules/, критичные
  инварианты. Никогда не разрастаются (правило: детали живут в rules/);
- **ADR-lite:** каждое значимое решение (выбор либы, отступление от правила) —
  файл в `docs/decisions/` по шаблону: контекст → решение → последствия. Пишет
  агент, одобряет пользователь; следующая сессия не переизобретает и не
  переспоривает решённое;
- **Правило актуализации:** скилл `feature` завершается проверкой «изменил
  поведение/структуру — обнови manifest / rules / спеку»; протухшие доки хуже
  отсутствующих;
- **Язык:** всё в репо — английский (код, доки, коммиты); общение агента с
  пользователем — на языке пользователя;
- **Git-конвенции** (`docs/rules/git.md`): conventional commits; коммит после
  каждого зелёного шага (см. свойства /liftoff); main — всегда рабочий; фичи —
  в ветках, merge после зелёного `verify`; pre-commit hook (lefthook) гоняет
  быстрый линт — тяжёлое остаётся в CI.

## 6. Флоу /liftoff

1. **Идея.** Интервью о идее пользователя; если идеи нет — генерация и проработка
   (перенос механики из проекта `ideas`: скоринг, уточнение ниши). Включает
   **fit-check**: идея, не ложащаяся в стек коробки (мобильное приложение,
   ML-пайплайн, realtime-heavy), — честное «Liftkit не для этого» с объяснением
   ДО генерации чего-либо, а не кривой результат.
2. **Фиксация.** `docs/idea.md` + мини-PRD: проблема, пользователь, 3–5 ключевых фич,
   что НЕ делаем в v1.
3. **Спеки.** Генерация спек первых 2–3 фич по шаблонам из `docs/templates/`.
4. **Адаптация скелета.** Имя проекта, брендинг-минимум (токены), схема БД под
   доменную модель идеи, manifest.md.
5. **Первый запуск.** `pnpm dev` + смоук-проверка агентом; вручение «карты дальше»:
   какие скиллы когда звать, плейбуки (инженерные и бизнесовые, см. 5.5), roadmap.md.

Свойства: линейный, проходится один раз, каждый шаг оставляет git-коммит
(прогресс не теряется при обрыве сессии), можно перезапустить с шага N.

## 7. Границы MVP (что коробка НЕ гарантирует)

- Деплой, биллинг, emails, бизнес-плейбуки (pricing/landing/analytics/compliance/
  ai-integration) — только плейбуки; выполняет агент пользователя, за сторонние
  UI/API коробка не отвечает. Плейбук compliance — ориентир, не юридическая
  консультация (дисклеймер обязателен).
- Поддержка Codex CLI и других агентов — фаза 2 (AGENTS.md держим совместимым).
- Публичный `npx create-liftkit` с лицензионным ключом — фаза 2 (маркетинговая обёртка).
- Генератор идей как полноценный продукт — не входит; только интервью/проработка внутри /liftoff.

## 8. Качество и тестирование (самого продукта)

- **Golden-path e2e:** CI-прогон «чистый клон → bootstrap → скелет собирается,
  все уровни тестов (юниты, интеграционные, e2e) и гейты зелёные». Это же — материал для демо.
- Ручной прогон полного /liftoff на «чужой» машине перед релизом (2–3 бета-тестера
  из целевой аудитории, бесплатный доступ за фидбек).
- Скиллы тестируются на 2–3 реальных сгенерированных идеях (разные домены).

## 9. Продажа и маркетинг

- LemonSqueezy (разовая покупка) → доступ к приватному GitHub-репо.
  MVP: инвайт по GitHub-username (вручную либо простым вебхуком); автоматизация — позже.
- Лендинг: одна страница, демо-видео «идея → работающее приложение за ~15 минут»
  (запись реального /liftoff), цена, FAQ.
- Каналы: build-in-public в X, Product Hunt, Indie Hackers, r/SideProject.
- Лицензия покупателя: использование без ограничений для своих проектов (включая
  клиентские); перепродажа/редистрибуция самого шаблона запрещена (стандарт
  категории). Текст — `LICENSE.md` в репо.
- **Доставка обновлений** (обещание «все апдейты» надо выполнять механикой):
  покупатель стартует от template-копии и теряет git-связь с апстримом — поэтому
  каждый релиз коробки = версия в `CHANGELOG.md` (semver) + заметка «как применить
  к живому проекту». Применяет агент покупателя: инструкция в changelog пишется
  как промпт-план (агентский аналог migration guide). Новые проекты просто берут
  свежий template. Автоматика (`liftkit update`) — не MVP.

## 10. Риски и валидация

1. **Инкумбенты съедают «agent-ready» как фичу.** Защита: глубина процесса
   (онбординг + feature-цикл + плейбуки), а не код. Валидация: фидбек бета-тестеров —
   «чем это лучше supastarter + свои скиллы?».
2. **Бесплатные OSS-аналоги** (claude-saas-accelerator, aitmpl). Защита: целостный
   протестированный опыт, поддержка, обновления. Валидация: конверсия лендинга.
3. **«Выглядит как бесплатный репозиторий».** Защита: демо-видео с измеримым
   результатом, founding-цена $10. Валидация: первые 10 продаж.
4. **Нейминг:** коллизия с OSS UI-фреймворком «LiftKit» — проверить домен/узнаваемость,
   при необходимости переименовать до лендинга.

## 11. Фазы после MVP (роадмап)

- Фаза 2: публичный `npx create-liftkit` + лицензионные ключи; поддержка Codex CLI.
- Фаза 3: по спросу — деплой как гарантированный сценарий, библиотека плейбуков
  (аналитика, email-маркетинг), pro-тир.
