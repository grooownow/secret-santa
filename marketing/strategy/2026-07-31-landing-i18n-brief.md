# Многоязычный лендинг: постановка

Цель: маркетинговый сайт Gridfin на нескольких языках, где тексты живут как
**данные** (JSON), а не как вёрстка, — чтобы новый язык стоил одного прогона
перевода и одной проверки, а не переписывания страницы.

Работа делится на три независимо проверяемых куска: **SEO-исследование** →
**копирайт** → **инфраструктура контента и сборка**. Порядок жёсткий: копия,
написанная до анализа запросов, — это копия, которую придётся переписывать под
ключевые слова, а перевод до фиксации схемы — это перевод, который придётся
делать заново.

## Что в старом плане устарело

Раздел «Двуязычность» предполагал `?lang=ru` и подмену текста на клиенте из
одного JS-словаря. Для двух языков это нормально; для «основных языков» — нет:
один URL с клиентской подменой = **одна индексируемая страница**, то есть весь
нерусский и неанглийский трафик не существует для поиска. Заменяется на:

- URL с сегментом локали: `/en/`, `/ru/`, `/de/` … `/en/` — канонический корень;
- **отдельный статический HTML на локаль**, собранный из JSON на этапе сборки;
- `hreflang` на все локали + `x-default`, `<html lang>`, канонический URL на
  локаль, свой `sitemap.xml`.

Это по-прежнему «ничему ломаться»: один шаблон, один генератор, N готовых
файлов. Фреймворк не нужен.

## Архитектура контента (рекомендация, обсуждаемая)

**Исходники — два, не один.** RU и EN пишутся **людьми независимо**, каждый под
свой поиск: спрос на этих рынках разный, и английская копия, переведённая с
русской, промахивается мимо английских запросов (и наоборот). Остальные языки —
машинный перевод **с английского**, потому что словарь дев-инструментов
англоязычный.

**Один JSON на локаль**, ключи семантические и стабильные:

```
content/
  en.json     ← источник для MT
  ru.json     ← источник, человек
  de.json     ← MT + ревью
  schema.json ← набор ключей, длины, обязательность
```

```json
{
  "_meta": { "locale": "de", "source": "en", "status": "mt" },
  "hero": {
    "badge": { "text": "…", "from": "a1b2c3", "status": "mt" },
    "h1": { "text": "…", "from": "d4e5f6", "status": "mt-reviewed" }
  }
}
```

Четыре механики, которые делают ИИ-перевод поддерживаемым, а не одноразовым:

1. **Ключ — смысл, а не текст.** `hero.h1`, не `"Ship a real SaaS…"`. Правка
   исходной фразы не ломает связь с переводами.
2. **`from` — хэш исходной строки.** Изменилась английская строка — все переводы
   с этим хэшем автоматически «протухли», и видно, какие именно.
3. **`status`** — `human` / `mt` / `mt-reviewed`. Честно видно, что носитель
   языка ещё не читал.
4. **Глоссарий непереводимого** — `Gridfin`, `Claude Code`, `Next.js`, `Vercel`,
   `PGlite`, `shadcn/ui`, имена скиллов (`/gridfin`, `/feature`). Переведённый
   `/feature` — сломанная инструкция, а не стилистическая вольность.

**SEO-поля не переводятся, а пишутся:** `seo.title`, `seo.description`,
`seo.slug` для каждой локали — из её собственного исследования. Для MT-локалей
это осознанный компромисс: либо оставляем английские, либо делаем беглый
рисёрч по каждой (решение фазы 0).

**Проверка — скриптом, а не глазами** (`pnpm i18n:check`, философия репозитория):
одинаковый набор ключей во всех локалях; нет пустых строк; плейсхолдеры
совпадают; длины в бюджете (h1 ≤ 60, meta description 150–160 — немецкий длиннее
английского на ~25% и ломает вёрстку); термины из глоссария не переведены;
протухшие переводы перечислены. Красный выход = не собираем.

## Фазы

**Фаза 0 — решения (нужен ответ Кати).** Список открытых вопросов ниже.

**Фаза 1 — SEO-исследование.** Отдельный документ
`docs/marketing/seo/2026-XX-XX-keyword-research.md`:

- Портрет покупателя и карта интентов (кто и что вбивает в поиск на каждом шаге).
- Кластеры запросов **отдельно для EN и RU**: seed-термины («claude code
  starter», «ai saas boilerplate», «next.js saas starter tests», «стартер для
  claude code»…), группировка по интенту, для каждого кластера — кто уже
  ранжируется и какой тип страницы.
- **Проверка коллизии бренда**: существует OSS UI-фреймворк «LiftKit» — что
  реально выдаёт поиск по бренду и что с этим делать (уточняющая формулировка
  «Liftkit for Claude Code», schema.org, домен). Это отдельный вывод, а не
  сноска: от него зависит имя домена.
- Разбор конкурентов: ShipFast, MakerKit, Supastarter, next-forge, gstack,
  Archon — их H1, title, description, на какие запросы метят.
- Итог: карта «кластер → блок лендинга», кандидаты title/description на локаль,
  список слов, которые обязаны быть в тексте.
- **Честное ограничение:** доступа к Ahrefs/Semrush нет; частотности будут
  качественными оценками по выдаче, автодополнению и связанным запросам. Если
  Катя даст выгрузку — цифры станут настоящими. Это указывается в документе, а
  не выдаётся за данные.

**Фаза 2 — русская копия.** Пройти `landing-copy.md` блок за блоком: выбрать A
или B (миксовать можно), довести до финального текста, вписать ключевые слова из
фазы 1 без порчи языка. Результат — `docs/marketing/landing-copy-ru-final.md`.

**Фаза 3 — английская копия.** Не перевод: авторская копия под английские
кластеры, той же структуры и тех же ключей.

**Фаза 4 — схема и JSON.** Вынести обе копии в `content/{ru,en}.json` по схеме
выше, написать `schema.json`, скрипт `i18n:check` и глоссарий. Тесты на скрипт —
по правилам репозитория (доказать, что падает).

**Фаза 5 — остальные языки.** MT с английского, прогон `i18n:check`, пометка
`status: mt`. Ревью носителем — отдельная задача на потом, не блокер.

**Фаза 6 — сборка и деплой.** Генератор `content/*.json` + шаблон →
`dist/<locale>/index.html`, hreflang, sitemap, canonical; переключатель языка,
сохраняющий путь; деплой на Vercel; аналитика с первого дня (раздел 6 старого
плана).
